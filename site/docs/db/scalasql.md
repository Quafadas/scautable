# ScalaSql integration

The `scalasql` module lets you point [scalasql](https://github.com/com-lihaoyi/scalasql) at a JDBC database and get a fully typed table that pushes queries down to the database. The schema is inferred at *compile time*, with no case class or codegen step.

The compiler needs to know each table's columns. The recommended way to provide them is a **schema snapshot**: a JSON file you generate once with credentials and then compile from without any. Your build tool, Metals and CI never need database credentials. Only the running program does.

| Step | Needs credentials | How often |
|---|---|---|
| 1. Write the snapshot | yes | when the schema changes |
| 2. Compile | no | every edit |
| 3. Run | yes | every run |

The examples below use the Postgres [world](https://www.postgresql.org/ftp/projects/pgFoundry/dbsamples/world/) sample database. The same steps work for `H2` and `MsSqlServer`.

## Project layout

```
my-project/
├── project.scala                  // main build: reads the snapshot
├── src/…                          // your DB.sqlTable calls
├── schemas/
│   └── scautable-db-schema.json   // generated by step 1, safe to commit
└── tools/
    └── snapshot.scala             // step 1, kept out of the main build
```

## Step 1: write the snapshot

The snapshot script is an ordinary program. It uses no macros, so it compiles without credentials, and it reads the connection details from its own environment when it runs:

```scala
// tools/snapshot.scala
//> using dep io.github.quafadas::scautable-db:@VERSION@
//> using dep org.postgresql:postgresql:42.7.13   // your JDBC driver

import io.github.quafadas.scautable.db.*

// Every name you pass to DB.sqlTable / DB.table, exactly as written in your code
val tables = List("country", "city", "countrylanguage")
// Every SQL string you pass to DB.query, exactly as written
val queries = List.empty[String]

@main def snapshot(): Unit =
  val conn = ConnectionResolver.openConnection() // reads SCAUTABLE_DB_* at runtime
  try
    val t = tables.map(n => s"table:$n" -> SchemaSnapshot.fromTable(conn, n))
    val q = queries.map(s => s"query:$s" -> SchemaSnapshot.fromQuery(conn, s))
    SchemaSnapshot.write((t ++ q).toMap, "schemas/scautable-db-schema.json")
  finally conn.close()
```

Run it from a terminal with the credentials exported:

```bash
export SCAUTABLE_DB_URL="jdbc:postgresql://localhost:5432/testdb"
export SCAUTABLE_DB_USER="testuser"
export SCAUTABLE_DB_PASSWORD="testpass"
scala-cli run tools/snapshot.scala
```

Run it from the project root: the output path is relative to the working directory. `SchemaSnapshot.write` replaces the whole file, so the lists must cover every table and query in your code. Keys are the strings exactly as written: `"dbo.Orders"` and `"Sales.dbo.Orders"` are different keys.

## Step 2: compile from the snapshot

Put the snapshot directory on the compile classpath, and keep the snapshot script out of the main build:

```scala
// project.scala
//> using dep io.github.quafadas::scautable-scalasql:@VERSION@
//> using dep org.postgresql:postgresql:42.7.13
//> using resourceDirs schemas
//> using exclude tools/*
```

With Mill, add the resources to the compile classpath with `override def compileResources = super.compileResources() ++ resources()`.

Now `DB.sqlTable` gets its types from the file:

```scala
import io.github.quafadas.scautable.scalasql.*
import io.github.quafadas.scautable.db.{DB, Postgres}
import scalasql.PostgresDialect.*
import scalasql.simple.{*, given}
import io.github.quafadas.table.*

@main def run(): Unit =
  val db = DB.connection[Postgres]
  val country = DB.sqlTable[Postgres]("country")
  val city = DB.sqlTable[Postgres]("city")
  val countrylanguage = DB.sqlTable[Postgres]("countrylanguage")

  db.run(country.select.take(10)).ptbln
  db.run(city.select.take(10)).ptbln
  db.run(countrylanguage.select.take(10)).ptbln

  db.run(city.select.sumBy(_.population))
```

## Step 3: run with credentials

`DB.connection` opens its JDBC connection lazily, on the first `db.run`, using `SCAUTABLE_DB_URL`, `_USER` and `_PASSWORD` from the running program's environment:

```bash
export SCAUTABLE_DB_URL=... SCAUTABLE_DB_USER=... SCAUTABLE_DB_PASSWORD=...
scala-cli run . --main-class run
```

[Database schemas without credentials at compile time](db.md) covers keeping credentials off disk (for example with a secrets manager), VS Code launch configurations, and troubleshooting.

## When the schema changes

Re-run the snapshot script, then force a rebuild (`scala-cli clean .`, "Metals: Clean compile workspace" or `./mill clean`). Incremental compilation does not notice when the snapshot file changes, so code that is already compiled keeps the old types until you rebuild.

## Alternative: a live connection at compile time

If `SCAUTABLE_DB_URL` is visible to the compiler's JVM, the macros read the schema straight from the database and ignore the snapshot. This suits a quick experiment, but it is hard to arrange in practice. With scala-cli and Metals, the compiler is the long-running Bloop daemon. Bloop doesn't see variables you export after it started, and any credentials you do give it are exposed to every project it compiles.

If you want to try it anyway, export the variables in a terminal, stop Bloop (`scala-cli --power bloop exit`), and compile from that same terminal so the new Bloop inherits them. Then connect Metals to that build server. Once the variable is set, the live connection always wins: if it fails, compilation fails instead of falling back to the snapshot.

## Connection configuration

Schema inference with a live connection, the snapshot script and the runtime `DbApi` all read the same three settings, `SCAUTABLE_DB_URL`, `SCAUTABLE_DB_USER` and `SCAUTABLE_DB_PASSWORD`. Each is looked up as a JVM system property first, then as an environment variable.

You select a dialect via a `DbFlavour` marker type (`H2`, `Postgres`, `MsSqlServer`, ...) — this determines both the scalasql dialect used to build queries and which `TypeMapper`s are summoned for each column.

## `DB.sqlTable` — infer a table's schema

`DB.sqlTable[F]("tableName")` reads the schema of `tableName` at compile time, from the snapshot or a live connection, and returns a `NamedTupleTable` — a scalasql `Table` whose row type is an anonymous `NamedTuple`. `tableName` may include a schema qualifier: `"schema.table"` or just `"table"`. On servers that host several databases, `"catalog.schema.table"` reaches another one through the same connection, e.g. `DB.sqlTable[MsSqlServer]("OtherDb.dbo.Customers")`.


Constructing `countries` never opens a network connection — its schema is resolved at compile time, from the snapshot or a live connection.

## `DB.connection` — get a matching `DbApi`

`DB.connection[F]` gives you a lazily-connecting scalasql `DbApi`, wired from the same `SCAUTABLE_DB_URL` / `_USER` / `_PASSWORD` names, for the dialect `F`. It is not table-specific, so it takes no table name — call it once and reuse it across tables:

```scala
val db = DB.connection[H2]

val big = db.run(countries.select.filter(_.population > 1_000_000))
```

The underlying JDBC connection is opened lazily on first use (e.g. the first `db.run(...)` call), not when `db` is constructed.

## `DB.sqlConnectionAndTable` — both at once

If you want the table and a matching connection together, `DB.sqlConnectionAndTable[F]("tableName")` returns a `(DbApi, NamedTupleTable)` pair in one call:

```scala
val (db, countries) = DB.sqlConnectionAndTable[H2]("country")

db.run(countries.select.filter(_.population > 1_000_000))
```

## Streaming a query to CSV

`db.run` collects every row into memory. For a large result, `db.stream` returns a `geny.Generator` that reads rows from the JDBC result set as they are consumed, and `writeCsvGenerator` writes each row to disk as it arrives. The full result is never held in memory:

```scala
val out = db.stream(city.select.filter(_.population > 100_000))
  .writeCsvGenerator(path = Some(os.pwd / "big-cities.csv"))
```

It takes the same options as `writeCsv` (`includeHeaders`, `delimiter`, `quote`), replaces any existing file, and returns the path it wrote. With no `path`, it writes to a temporary file. The result set stays open only while the file is being written.

## Full query DSL

Because `NamedTupleTable` is a genuine scalasql `Table`, the whole query DSL is available: `select`, `filter`, `map`, `join`, `sumBy` / `avgBy` / `minBy` / `maxBy` / `countBy`, `insert`, `update`, `delete`, and so on. Column identifiers are exactly the DB column names — no camelCase mapping is applied.

## Identifier handling

Table names are always quoted via the dialect's `escape` mechanism, and column names are passed through unmodified. If you configure your own `scalasql.Config`, use `columnNameMapper = identity` to avoid any camelCase-to-snake_case conversion.
